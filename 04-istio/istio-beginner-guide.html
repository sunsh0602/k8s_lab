초보자를 위한 서비스 메시 입문

Istio, 처음부터 이해하기

서비스가 10개, 100개로 늘어나면 "누가 누구에게 어떻게 말을 거는지" 관리가 지옥이 됩니다. Istio는 이 문제를 애플리케이션 코드를 건드리지 않고 해결하는 도구입니다.

Istio 없이

각 서비스가 재시도·타임아웃·인증을 직접 구현. 서비스가 늘수록 연결선이 기하급수적으로 얽힘.

Istio 사용 시

모든 통신이 사이드카 프록시를 거쳐 이루어지고, 규칙은 중앙(Istiod)에서 한 번에 관리.

01

서비스 메시가 뭔가요?

한 문장으로: 서비스끼리 대화하는 방식을 관리해주는 인프라 계층입니다.

마이크로서비스 아키텍처에서는 하나의 요청을 처리하기 위해 여러 서비스가 서로를 호출합니다. 이때 "타임아웃은 몇 초로 할지", "실패하면 몇 번 재시도할지", "누가 누구를 호출할 권한이 있는지" 같은 규칙이 필요한데, 이걸 서비스마다 코드로 구현하면 서비스 100개는 곧 100가지 방식이 생기는 셈입니다.

비유로 이해하기 각 건물(서비스)마다 자체 경비원을 고용하는 대신, 도시 전체에 공통 교통 시스템(신호등, 표지판, CCTV)을 까는 것과 비슷합니다. 건물은 자기 할 일만 하고, 도로 규칙은 도시(서비스 메시)가 관리합니다.

Istio는 이 "공통 교통 시스템" 역할을 하는 오픈소스 서비스 메시입니다.

02

어떻게 동작하나요? — 컨트롤 플레인과 데이터 플레인

Istio는 크게 두 개의 층으로 나뉩니다: 지시를 내리는 곳과 실제로 트래픽이 지나가는 곳.

Istiod (컨트롤 플레인)

서비스 발견, 트래픽 규칙 구성, 인증서 관리를 담당하는 중앙 관리자입니다. 사람이 kubectl apply로 규칙을 등록하면, Istiod가 이걸 이해해서 각 사이드카에게 전달합니다.

Envoy 사이드카 (데이터 플레인)

내 애플리케이션 파드마다 자동으로 하나씩 따라붙는 작은 프록시입니다. 앱 코드는 전혀 몰라도, 들어오고 나가는 모든 트래픽이 이 사이드카를 거치면서 재시도·타임아웃·암호화·권한 검사가 적용됩니다.

핵심 포인트 애플리케이션 코드는 단 한 줄도 바뀌지 않습니다. 사이드카가 네트워크 트래픽을 가로채서 규칙을 대신 적용해주기 때문입니다.

Ingress / Egress Gateway

메시의 "정문"과 "후문"입니다. Ingress Gateway는 외부에서 들어오는 트래픽을 받고, Egress Gateway는 메시 안에서 바깥(외부 API 등)으로 나가는 트래픽을 관리합니다.

03

규칙은 어떻게 정의하나요? — 주요 리소스

Istio는 Kubernetes에 새로운 리소스 타입(CRD)을 추가해서, YAML로 트래픽 규칙을 선언합니다.

리소스하는 일쉽게 말하면
Gateway 메시 경계에서 들어오고 나가는 트래픽을 허용/제어 건물의 정문 — 어떤 포트로 누가 들어올 수 있는지
VirtualService 요청을 어디로 라우팅할지 규칙 정의 안내데스크 — "이 요청은 v2로 보내주세요"
DestinationRule 목적지 서비스의 로드밸런싱·연결 정책 설정 창구 운영 규칙 — "한 창구당 몇 명까지"
ServiceEntry 메시 바깥의 외부 서비스를 메시 안에 등록 외부 손님을 방문자 명단에 등록
AuthorizationPolicy 누가 누구를 호출할 수 있는지 접근 제어 출입 카드 — 이 방은 이 팀만 출입 가능
RequestAuthentication 요청의 신원을 어떻게 확인할지 정의 신분증 검사 방식 지정
04

설치해보기 (NKS 기준)

아래 순서는 순서가 중요합니다 — 앞 단계가 끝나야 다음 단계가 의미를 가집니다.

istioctl 다운로드

istioctl은 Istio를 설치·점검·디버깅하는 커맨드라인 도구입니다.

oras pull ${REGISTRY}/istioctl-tool:${VERSION} tar -zxvf istio-${VERSION}-linux-amd64.tar.gz cd istio-${VERSION} export PATH=$PWD/bin:$PATH

프로파일 선택 후 설치

Istio는 용도에 맞는 설치 프로파일을 제공합니다 — 학습/테스트는 demo, 운영 환경은 minimal/production을 씁니다.

istioctl install --set profile=demo --set hub=${REGISTRY} -y

설치 확인

istio-system 네임스페이스에 컨트롤 플레인과 게이트웨이가 떴는지 확인합니다.

kubectl get all -n istio-system

istiod 1개, ingress/egress gateway 각 1개 — 총 3개 파드가 Running이면 성공입니다.

네임스페이스에 사이드카 자동 주입 활성화

이 레이블을 붙인 네임스페이스에 생성되는 모든 새 파드에는 Envoy 사이드카가 자동으로 따라붙습니다.

kubectl label namespace default istio-injection=enabled
05

예제로 감 잡기 — Bookinfo

Istio 공식 예제 애플리케이션으로, 여러 마이크로서비스가 서로 호출하는 전형적인 구조를 보여줍니다.

productpage메인 화면
↓ 호출
details책 정보
reviewsv1 · v2 · v3
reviews ↓ 호출
ratings평점

주목할 점은 reviews 서비스에 버전이 3개라는 것입니다. 이런 구조에서 "트래픽의 90%는 v1로, 10%는 v3로" 같은 카나리 배포 규칙을 VirtualService 하나로 선언할 수 있는 것이 Istio의 강점입니다.

kubectl apply -f samples/bookinfo/platform/kube/bookinfo.yaml

배포 후 파드 상태를 보면 READY 칸이 2/2로 보입니다 — 앱 컨테이너 1개 + 사이드카 컨테이너 1개라는 뜻입니다.

kubectl get pods # NAME READY STATUS # productpage-v1-... 2/2 Running

실제 서비스
kubectl apply -f samples/bookinfo/networking/bookinfo-gateway.yaml # 규칙에 문제가 없는지 검사 istioctl analyze

규칙이 정상이면 No validation issues found 메시지가 나옵니다. 이제 게이트웨이의 접속 주소를 확인합니다:

export INGRESS_HOST=$(kubectl -n istio-system get service istio-ingressgateway \ -o jsonpath='{.status.loadBalancer.ingress[0].ip}') export INGRESS_PORT=$(kubectl -n istio-system get service istio-ingressgateway \ -o jsonpath='{.spec.ports[?(@.name=="http2")].port}') export GATEWAY_URL=$INGRESS_HOST:$INGRESS_PORT curl http://${GATEWAY_URL}/productpage
참고 인터넷이 연결된 환경에서는 LoadBalancer의 외부 IP를 쓰고, 폐쇄망 환경에서는 NodePort 방식으로 접속 주소를 받아옵니다.
07

정리하기

테스트가 끝나면 리소스를 순서대로 되돌립니다. 애플리케이션 → 게이트웨이 → Istio 자체 순서입니다.

# 예제 앱만 삭제 kubectl delete -f samples/bookinfo/networking/bookinfo-gateway.yaml kubectl delete -f samples/bookinfo/platform/kube/bookinfo.yaml # Istio 전체 삭제 istioctl uninstall --purge -y kubectl delete namespace istio-system kubectl label namespace default istio-injection-
주의 istioctl uninstall --purge는 클러스터 전체의 Istio 구성 요소를 제거합니다. 다른 팀이 같은 클러스터를 쓰고 있다면 영향 범위를 먼저 확인하세요.

한눈에 정리

  • 서비스 메시 = 서비스 간 통신을 앱 코드 밖에서 관리하는 인프라 계층
  • 컨트롤 플레인(Istiod)이 규칙을 정하고, 데이터 플레인(Envoy 사이드카)이 실제로 실행
  • Gateway·VirtualService·DestinationRule로 "누가 들어오고, 어디로 가고, 어떤 정책을 쓸지" 선언
  • 파드가 2/2 Ready로 보이면 사이드카가 정상 주입된 것
  • 학습은 demo 프로필, 운영은 minimal/production 프로필
