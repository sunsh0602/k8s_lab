Observability 스택 구축 가이드

Alloy + LGTM으로 관찰 가능성 갖추기

"장애가 나면 뭘 봐야 하지?"에 대한 답을 하나의 스택으로 통일하는 방법. Grafana Labs가 만든 수집기(Alloy)와 저장/조회 4종 세트(LGTM)를 함께 구축합니다.

📜

로그 (Logs)

"무슨 일이 있었나" — 이벤트 기록

📈

메트릭 (Metrics)

"지금 수치가 어떤가" — 시계열 숫자

🔗

트레이스 (Traces)

"요청이 어디를 거쳤나" — 호출 경로

01

왜 로그·메트릭·트레이스를 따로 볼까?

셋 다 "시스템 상태를 아는 방법"이지만, 던지는 질문이 다릅니다.

비유로 이해하기 병원 진료와 같습니다. 혈액검사(메트릭)는 "지금 수치가 정상 범위인가"를 빠르게 알려주고, 진료 기록(로그)은 "언제 무슨 증상이 있었는지" 시간순 기록을 남기고, 정밀 촬영(트레이스)은 "문제가 몸의 어느 경로를 거쳐 발생했는지" 추적합니다. 셋 중 하나만으로는 정확한 진단이 어렵습니다.

MSA 환경에서 요청 하나가 서비스 5개를 거친다면: 메트릭으로 "reviews 서비스 응답시간이 튀었다"는 걸 감지하고, 트레이스로 "어느 호출 구간에서 느려졌는지" 좁히고, 로그로 "그 순간 정확히 어떤 에러가 찍혔는지" 확인하는 식으로 셋이 서로를 보완합니다.

02

구성 요소 — Alloy와 LGTM

LGTM은 네 글자 각각이 하나의 컴포넌트를 가리키는 약어이고, Alloy는 이 넷에게 데이터를 실어나르는 배달원입니다.

이름역할담당 축
Grafana Alloy 각 노드/파드에서 로그·메트릭·트레이스를 수집해 알맞은 저장소로 전달하는 통합 에이전트 (OpenTelemetry Collector 호환) 수집기
Loki 로그 저장소. Elasticsearch처럼 본문 전체를 인덱싱하지 않고 레이블만 인덱싱해서 훨씬 가볍게 동작 로그
Grafana Loki·Mimir·Tempo를 한 화면에서 조회하는 시각화 대시보드 시각화
Tempo 분산 트레이싱 저장소. OTLP로 수집한 스팬(span)을 저장하고 요청 흐름을 그래프로 재구성 트레이스
Mimir Prometheus 호환 메트릭 저장소. 장기 보관과 수평 확장이 어려운 단일 Prometheus의 한계를 보완 메트릭

Alloy가 이전 Grafana Agent와 다른 점

Grafana Agent는 2024년부로 Alloy로 통합·대체되었습니다. Alloy는 OpenTelemetry Collector와 호환되는 파이프라인 구성 언어를 쓰기 때문에, "수집 → 가공(필터링/레이블링) → 전달"을 하나의 설정 파일로 선언할 수 있고, 나중에 다른 벤더의 OTel 백엔드로 옮기기도 비교적 쉽습니다.

03

장단점

도입 전에 이 스택이 정말 필요한 규모인지 판단하는 데 참고하세요.

장점

  • 로그·메트릭·트레이스를 Grafana 한 화면에서 넘나들며 조회 (Explore 뷰의 연계 탐색)
  • 전 구성 요소 오픈소스 — Datadog·New Relic 대비 라이선스 비용 없음
  • Loki는 레이블 기반 인덱싱이라 Elasticsearch보다 스토리지·리소스 사용량이 적음
  • Mimir·Loki·Tempo 모두 수평 확장 아키텍처 — 트래픽이 커져도 같은 스택으로 대응 가능
  • Alloy가 OpenTelemetry 표준을 따라서 특정 벤더에 코드가 종속되지 않음
  • Grafana Labs가 4개 컴포넌트를 모두 만들어서 버전 호환성 문제가 적음

단점

  • 운영해야 할 컴포넌트가 5개(Alloy+LGTM)로 늘어나 초기 학습 곡선이 가파름
  • LogQL은 Elasticsearch의 풀텍스트 검색만큼 유연하지 않음 (레이블을 미리 잘 설계해야 함)
  • Mimir/Loki를 제대로 쓰려면 객체 스토리지(S3/MinIO)가 사실상 필요 — 랩 환경엔 추가 부담
  • Alloy의 설정 언어(Alloy syntax, 구 River)가 비교적 최근에 나와 레퍼런스/커뮤니티 자료가 적음
  • 노드 1~2대짜리 소규모 클러스터에는 과한 스펙일 수 있음 (단일 Prometheus+Grafana로 충분한 경우도 많음)
  • 장애 시 "관찰 도구 자체가 원인"이 되는 경우 디버깅 대상이 하나 더 늘어남

이 스택이 맞는 상황인가?

서비스가 여러 개고, 서로 호출하는 MSA 구조인가그렇다 → Alloy+LGTM 적합
노드가 1~2대인 개인 랩/토이 프로젝트인가그렇다 → Prometheus+Grafana만으로 충분
분산 트레이싱(요청 흐름 추적)이 꼭 필요한가그렇다 → Tempo 포함된 이 스택이 유리
로그를 풀텍스트로 자유롭게 검색해야 하는가그렇다 → Loki보다 Elasticsearch 계열 고려
04

설치 매뉴얼 (단일/소규모 클러스터 기준)

운영 환경은 각 컴포넌트를 분산(마이크로서비스) 모드로 배포하지만, 랩처럼 노드가 적을 땐 모놀리식(단일 바이너리) 모드로 설치해 리소스를 아낍니다.

랩 환경 고려사항 Loki·Mimir·Tempo는 기본적으로 오브젝트 스토리지(S3 호환)에 데이터를 저장하도록 설계되어 있습니다. 별도 S3/MinIO가 없다면 각 차트의 filesystem 스토리지 모드로 설치해 로컬 디스크에 저장하도록 구성합니다. 데이터 보존 기간이 짧고 HA가 없다는 점을 감안하세요.
1

네임스페이스 준비 & Helm repo 확인

Grafana 공식 Helm 저장소 하나로 LGTM 전체를 설치할 수 있습니다.

kubectl create namespace monitoring helm repo add grafana https://grafana.github.io/helm-charts helm repo update grafana
2

Loki 설치 (로그)

SingleBinary 배포 모드 + filesystem 스토리지로 설치합니다.

helm install loki grafana/loki -n monitoring \ --set loki.commonConfig.replication_factor=1 \ --set loki.storage.type=filesystem \ --set singleBinary.replicas=1
3

Mimir 설치 (메트릭)

모놀리식 모드로 설치해 Prometheus 역할을 대체합니다. (기존 kube-prometheus-stack의 Prometheus를 계속 쓰고 Mimir는 장기 보관용으로만 붙이는 구성도 가능)

helm install mimir grafana/mimir-distributed -n monitoring \ --set mimir.structuredConfig.limits.max_global_series_per_user=0 \ --set minio.enabled=true

실습 편의상 차트 내장 minio.enabled=true 옵션으로 간이 오브젝트 스토리지를 함께 띄웁니다.

4

Tempo 설치 (트레이스)

helm install tempo grafana/tempo -n monitoring \ --set tempo.storage.trace.backend=local
5

Grafana 설치 & 데이터소스 연결

Grafana를 설치한 뒤, Loki·Mimir·Tempo를 데이터소스로 등록합니다.

helm install grafana grafana/grafana -n monitoring \ --set persistence.enabled=true \ --set datasources."datasources\.yaml".apiVersion=1 \ --set datasources."datasources\.yaml".datasources[0].name=Loki \ --set datasources."datasources\.yaml".datasources[0].type=loki \ --set datasources."datasources\.yaml".datasources[0].url=http://loki-gateway.monitoring

Mimir(Prometheus 호환 API)와 Tempo도 같은 방식으로 datasources.yaml에 추가합니다.

6

Alloy 설치 (수집기, DaemonSet)

모든 노드에서 로그·메트릭을 걷어 각각 Loki·Mimir로, 애플리케이션이 보내는 OTLP 트레이스는 Tempo로 전달하도록 구성합니다.

helm install alloy grafana/alloy -n monitoring \ --set-string 'alloy.configMap.content= loki.write "default" { endpoint { url = "http://loki-gateway.monitoring/loki/api/v1/push" } } prometheus.remote_write "default" { endpoint { url = "http://mimir-nginx.monitoring/api/v1/push" } } otelcol.exporter.otlp "tempo" { client { endpoint = "tempo.monitoring:4317" } } '
참고 실제 운영에서는 위 파이프라인을 별도 values.yaml 파일로 분리해서 관리하는 것을 권장합니다. 인라인 --set-string은 예시일 뿐입니다.
7

설치 확인

kubectl get pods -n monitoring kubectl get svc -n monitoring | grep grafana

Grafana에 접속해 Explore 메뉴에서 Loki/Mimir/Tempo 데이터소스로 각각 조회가 되면 성공입니다.

한눈에 정리

  • 관찰 가능성의 3대 축: 로그(무슨 일) · 메트릭(지금 수치) · 트레이스(어디를 거쳤나)
  • LGTM = Loki(로그) + Grafana(시각화) + Tempo(트레이스) + Mimir(메트릭)
  • Alloy는 이 넷에게 데이터를 실어나르는 통합 수집기, OpenTelemetry 호환
  • 장점: 통합 조회, 오픈소스, 수평 확장 / 단점: 컴포넌트 수 많음, 객체 스토리지 필요, 학습 곡선
  • 소규모 클러스터라면 전체 스택보다 Prometheus+Grafana만으로 시작하는 것도 합리적 선택
  • 랩 환경에서는 각 컴포넌트를 모놀리식/filesystem 모드로 설치해 리소스 절약
