Vault 설치 & 초기화

Ubuntu 24.04 호스트(master)에 APT로 직접 설치

APT 설치 + Raft 설정 + systemd 기동

HashiCorp APT 저장소 등록 → vault 패키지 설치 → /etc/vault.d/vault.hcl 작성 → systemd 서비스 기동.

# 설정 파일 핵심 내용 ui = true disable_mlock = false # Vault 2.x부터 명시 필수 storage "raft" { path = "/opt/vault/data" } listener "tcp" { address = "0.0.0.0:8200" tls_disable = 1 # 랩 환경, 내부망 전용 } api_addr = "http://192.168.137.10:8200" cluster_addr = "http://192.168.137.10:8201"
결과
Vault 서비스가 active (running), Sealed 상태로 대기

Operator Init & Unseal

5개의 Unseal Key(threshold 3)와 Root Token을 발급받고, 3개 키로 Unseal 처리.

vault operator init -key-shares=5 -key-threshold=3 vault operator unseal # 3회 반복
결과
Sealed: false, HA Mode: active — 정상 서비스 시작
Unseal Key와 Root Token은 패스워드 매니저 등 안전한 곳에 별도 보관 (문서에는 저장하지 않음)

KV v2 Secrets Engine 활성화

vault secrets enable -version=2 -path=secret kv vault kv put secret/app/database username=<DB_USERNAME> password=<DB_PASSWORD>
결과
secret/app/database 경로에 테스트 시크릿 저장 확인

Kubernetes Auth Method 연동

Pod의 ServiceAccount로 Vault에 인증할 수 있도록 구성

Auth Method 활성화 & 클러스터 등록

vault auth enable kubernetes vault write auth/kubernetes/config \ kubernetes_host="https://192.168.137.10:6443" \ kubernetes_ca_cert=@ca.crt \ token_reviewer_jwt="<ServiceAccount JWT>"

정책(Policy) & 역할(Role) 생성

app-policy로 읽기 권한 범위를 제한하고, app-role로 어떤 ServiceAccount가 이 정책을 받을지 결정.

구성 요소값
Policy 경로secret/data/app/*, secret/metadata/app/* (read, list)
Role 이름app-role
허용 ServiceAccountdefault (namespace: default)
연결된 Policyapp-policy
결과
default 네임스페이스의 default SA를 가진 Pod만 secret/app/*를 읽을 수 있게 제한됨

Vault Agent Injector 배포 & 검증

Helm으로 Injector만 설치 (Vault 서버는 호스트에서 계속 운영)

Helm 설치 (server 비활성화, injector만)

helm repo add hashicorp https://helm.releases.hashicorp.com kubectl create namespace vault # values-injector.yaml server: enabled: false injector: enabled: true externalVaultAddr: "http://192.168.137.10:8200" tolerations: - key: node-role.kubernetes.io/control-plane operator: Exists effect: NoSchedule helm install vault hashicorp/vault -n vault -f values-injector.yaml
결과
vault-agent-injector Pod 1/1 Running, MutatingWebhook 등록 완료
worker1 노드가 NotReady 상태라 master(control-plane)에 toleration을 추가해 스케줄링함

테스트 Pod 생성 (annotation 기반 자동 주입)

metadata: annotations: vault.hashicorp.com/agent-inject: "true" vault.hashicorp.com/role: "app-role" vault.hashicorp.com/agent-inject-secret-db: "secret/data/app/database" vault.hashicorp.com/agent-inject-template-db: | {{- with secret "secret/data/app/database" -}} username: {{ .Data.data.username }} password: {{ .Data.data.password }} {{- end -}}
Troubleshooting

403 Permission Denied — Kubernetes Auth 실패

증상
init container(vault-agent-init) 로그에 PUT auth/kubernetes/login → 403 permission denied 반복
원인
token_reviewer_jwt를 kubectl create token default로 발급 — 기본 1시간 후 만료되는 단기 토큰이라 시간이 지나 인증 실패
해결
전용 vault-auth ServiceAccount 생성 → kubernetes.io/service-account-token 타입 Secret으로 장기 토큰 발급 → system:auth-delegator ClusterRole 바인딩 → Vault 설정을 새 토큰으로 갱신
kubectl apply -f vault-auth-sa.yaml # ServiceAccount + Secret + ClusterRoleBinding vault write auth/kubernetes/config \ kubernetes_host="https://192.168.137.10:6443" \ token_reviewer_jwt="<vault-auth 장기 토큰>" \ kubernetes_ca_cert=@ca.crt

최종 검증

kubectl exec vault-agent-test -c app -- cat /vault/secrets/db
username: <DB_USERNAME> password: <DB_PASSWORD>
결과
Pod 코드 수정 없이 /vault/secrets/db 파일로 시크릿이 자동 렌더링됨 — Vault ↔ Kubernetes 연동 검증 완료
